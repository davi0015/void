**Fixes**

- A launch that restores a thread no longer leaves the chat pane showing
  `Current thread should never be undefined`. Moving a thread's messages into its own
  log file made the startup landing wait on that file, and the sidebar rendered while
  the wait was still in flight — so the first render asked for a current thread that
  had not been published yet, threw, and the error boundary around the pane kept the
  throw on screen for the rest of the session. Relaunching repeated it, because the
  race is on every launch that reopens an existing conversation. The landing now
  publishes the thread first and lets the messages arrive into it, so the conversation
  appears as the read completes (#170)

- The chat pane's error boundary now retries instead of latching: a caught error is
  cleared when the current thread changes, the warning itself is clickable to retry,
  and the error and its component stack reach the console rather than being swallowed
  by the boundary. The startup race above is fixed at its source; this is what keeps
  the next one — a render that throws once while state is still arriving — a moment
  rather than a pane that can only be recovered by restarting (#170)

**Nothing was wrong with the stored conversations.** The throw happened while
rendering, after the messages had been read and converted into their log files, and
nothing on that path deletes or rewrites a stored message. A profile that showed this
error opens normally on this build, with its history intact.
