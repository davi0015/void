**Fixes**

- Terminal commands run to completion and return the output the command produced,
  not the output the terminal happened to be displaying. Three faults on that path,
  each of which looked like the agent ignoring an instruction:
  a multi-line command was disposed at its first line's completion, so a heredoc
  followed by `pytest` lost pytest and a multi-line script lost everything after its
  first line — the batch now appends a sentinel line and settles when it finishes,
  and its status is the first non-zero exit code rather than the first line's (#162);
  the output was read from the xterm buffer, which hard-wraps at the terminal width
  and keeps only the last ~1,030 rows, so a 300 KB file read back as 82,383
  characters with its first token missing — it now comes from the pty stream between
  the shell integration's OSC 633 markers (#164); and on a fresh window the
  command-detection check ran before the default profile resolved, concluded the
  shell could not report completion, and skipped both completion paths, so `echo`
  sat until the inactivity timeout — 21.5 s reported as a timeout on the previous
  build, 1.5 s reported as done on this one (#163)
- The agent is told which shell a new terminal runs, instead of discovering it from a
  syntax error. A cmd terminal no longer reports `running` while idle: cmd cannot
  attach shell integration on Windows, and the status fell back to `'running'`, which
  told the model to wait — the fallback is now `'unknown'`, and the terminal block
  says that a command there settles on inactivity. Creating a terminal no longer
  takes the caret out of the chat input; the cause was not the terminal, it was the
  sidebar re-rendering and re-creating the textarea, so focus is re-asserted after
  the panel opens rather than restored on a disconnected element (#160)
- A statement that meets another window's write lock on `state.vscdb` waits up to
  10 s instead of failing at once. On the read path the failure was a rejected
  startup read; on the write path it was worse than an error — it arrived on the
  statement's `error` event, the connection was marked erroneous, `END TRANSACTION`
  still committed, and the write was dropped while `flush()` reported success. That
  is how a large profile shows a window that does not open, or settings that do not
  stick (#159)

**New**

- Conversation messages leave the store the renderer mirrors at startup. A thread's
  messages live in `threads/<threadId>/messages.jsonl` under global storage — one
  record per line, `{"i":<index>,"m":<message>}`, append-only, folded by index with
  the last record winning — and the startup mirror now leaves the `void.chatMsg.*`
  keys out. The cost this removes is the transfer, and the transfer is what scales
  with conversation: above roughly 50 MB of messages a launch is linear in their
  size, 2.9 s at 395 MB, and those threads were never opened (#158). Reading the
  store in the main process still happens on every launch; that is unchanged here.
  The first launch after upgrading converts every thread's messages into its log
  before the window is built, so that one launch is slower. The old keys are left in
  the database — unmirrored, so they cost no launch time — which is what makes a
  downgrade still able to read the history it wrote.
- The agent can check something without leaving a project change behind.
  `write_scratch` and `delete_scratch` write under `<workspace>/.void/tmp/<threadId>/`
  through the file service rather than the edit service, so no diff zone is created
  and there is nothing to accept; `.void/.gitignore` contains `*`, so neither the
  folder nor its contents appear in git and the user's own `.gitignore` is untouched.
  The path is the only caller input that decides where a file lands, so absolute
  paths, drive letters, `..` and empty segments are rejected rather than clipped —
  at validation and again at call time — which is what keeps `delete_scratch` and
  `write_scratch` agreeing about the target. Scratch persists for the chat, because
  a follow-up turn may still want the script; one file is capped at 1 MB and one
  thread's scratchpad at 50 MB (#167)
- The external chat integration posts the thread's title with every message — the
  custom title, else the first user message excerpted to 80 characters — so a reply
  read out of context, the way a mobile notification shows one, still says which
  task it belongs to. The field is optional, and an older proxy ignores it (#168)

**Internal** — launch cost is measured by a test rather than argued from the code
(#158); the PR check seeds its module cache from `main` and splits the typecheck into
its own job, and the required check is now `Tests + hygiene (Linux)` (#161); the log
format, its file operations and the conversion have node tests, so the two places
that can silently lose a message run in seconds instead of under Electron.

**Known limits, stated rather than implied**

- A profile is no longer one file. `state.vscdb` holds thread metadata and the
  legacy message keys; `void/threads/` holds the logs. Copying only the database
  gives empty chats on this release — copy `User/globalStorage/void` as well.
- Downgrading to 1.4.0 opens converted threads and shows their history as of the
  upgrade. Messages sent under 1.5.0 are in the logs, which 1.4.0 does not read, and
  messages sent while downgraded stay invisible after upgrading again: the thread is
  still marked as a log thread, so the keys 1.4.0 wrote are not folded back in.
- `search_history` still loads a thread's messages on demand, so searching a large
  thread reads its whole log. An indexed range read is deferred, not forgotten.
- The end-to-end tier has still only ever run on Windows. CI compiles on
  `ubuntu-22.04` and runs the node tier, never the end-to-end tier, so the macOS and
  Linux artifacts are compiled and typechecked rather than behaviourally verified.
